# v0.2 library ergonomics implementation plan

Status: accepted for implementation on 2026-08-10.

## Audit

The v0.1 canonical boundaries are sound, but the default npm experience exposes
them too early. A first recommendation requires `schemaVersion`, `asOf`, a full
methodology configuration, and a catalog-bearing request. The same catalog and
scope are then repeated when a recommendation is instantiated and again when a
workout is reloaded or converted for evaluation. Set completion requires both a
membership ID and a set ID even though the active workout already contains the
relationship. Application code manually constructs generic metric arrays and
must defensively check optional properties after `ok` checks because programming
results are not discriminated unions.

The package entry point mixes canonical types, WASM ownership, runtime dispatch,
persistence orchestration, active-workout behavior, portable data, discovery,
and public errors in one 1,233-line file. The package has useful methodology
factories, but no documented preset or partial builder. Discovery metadata is
already versioned and UI-neutral, with field descriptions, types, enum choices,
units, ranges, defaults, and schema references; its main omission is the nested
advancement criteria fields. Browser and IndexedDB examples faithfully expose
the same repetition. Clean consumers test the packed artifact, which gives a
strong compatibility gate.

The direct Zig API is intentionally borrowed and allocation-free, but its
caller-owned recommendation storage contains only one exercise and rejects every
multi-exercise catalog. This is an artificial v0.1 result bound. The public C ABI
v2 already has the desired small shape: create/destroy a runtime and execute a
versioned canonical envelope into caller-owned bytes. No convenience expansion
is warranted there.

History confirms these shapes were deliberate staged vertical slices: typed Zig
recommendation preceded canonical/C/WASM dispatch, and npm workflows were added
as a thin orchestration layer. The v0.2 work therefore extends those layers; it
does not replace their contracts.

## Public API design

The default npm export will retain every v0.1 method and add an application
context created with `caudex.createProgram(options)`. A program binds catalog,
methodology, host scope, optional athlete/history/state and state revision. Its
`recommend()` and `evaluate()` methods construct complete canonical requests at
the call boundary using the injected clock. `startWorkout()` and `reloadWorkout()`
reuse the bound catalog and scope. The program retains host references and its
known accepted state revision, but it does not contain workout-programming logic
or mutate the engine. Persistence remains optional and all engine calls still
receive complete snapshots.

`caudex.runtime` will group direct canonical operations. Existing top-level
methods (`recommendSession`, `evaluatePerformance`, tracking, discovery,
portable operations, and `workflows`) remain compatible aliases in v0.2 and are
not deprecated yet: removing or warning on the only v0.1 entry points would add
migration cost without improving safety. Documentation will call `runtime` the
advanced layer and `createProgram` the normal application layer.

Programming `RecommendationResult` and `EvaluationResult`, methodology
validation, and portable outcomes will use discriminated unions where branches
are exclusive. The JSON shape is unchanged. Successful programming branches
will make their payload present; rejected branches will make `issues` present.
Mixed tracking batches remain unchanged because they genuinely contain multiple
outcomes.

Measurement helpers `lb`, `kg`, `reps`, `rpe`, `rir`, `seconds`, and `minutes`
will cover only existing canonical units/codes. Decimal input accepts a string,
safe integer, or finite number whose normal decimal spelling is non-exponential;
strings remain the escape hatch for exact values. Invalid signs, scale, range,
unsafe integers, NaN/infinity, and unsupported representations fail immediately
with a structured `CaudexMeasurementError`. Set result objects accept ergonomic
`reps`, `load`, `rpe`, and `rir` fields and convert once at the tracking command
boundary; canonical metric arrays remain accepted as `metrics`.

`ActiveWorkout.completeSet(setId, result)` will resolve the owning membership
from the current snapshot. IDs must be unique, the set must still exist and be
open, and the current revision is read immediately before dispatch, so a retained
handle does not cache stale parent relationships. The old object argument with
`membershipId`, `setId`, and `actual` remains supported. No per-set handles are
added: they would create more invalidation and reload semantics than the friction
justifies.

Double progression gains an explicit, inspectable `hypertrophy` preset builder.
It chooses only documented policy values and requires `initialLoad`; callers can
override every chosen field through a typed partial. The fully explicit factory
remains primary for applications that do not want a preset. No methodology
algorithm or implicit training decision moves to TypeScript.

Implementation modules will separate canonical/public types, errors,
measurements, methodology construction, runtime/WASM dispatch, and workflows.
The index remains the intentional entry point. Advanced `runtime` and
`canonical` subpaths will improve discoverability without exposing private
implementation files.

## Zig and C

Increase typed Zig `Output` to bounded per-exercise storage for a realistic
catalog, iterate deterministically over the validated catalog, and keep all
storage caller-owned. Add small constructors only where they remove repeated
parsing without concealing ownership. Tests will cover multiple exercises,
equipment configurations, memberships, and stable output. The one-exercise
error/documentation is removed; existing one-exercise behavior remains the same.

The C ABI, symbols, version, allocation rules, and request envelope remain
unchanged. Documentation will explicitly explain that C is a stable protocol/FFI
surface while TypeScript owns ecosystem-specific convenience.

## Rejected ideas

- No stateful workout algorithm, global current profile, implicit persistence,
  or process-global defaults.
- No TypeScript reimplementation of methodology decisions.
- No set/exercise handle graph in v0.2; ID resolution is the smaller lifecycle
  abstraction.
- No silent unit conversion or binary-float canonical representation.
- No large C convenience API and no ABI version bump.
- No opaque preset named merely `default`; every preset states its intent and
  resulting canonical configuration is inspectable.
- No canonical schema changes for facade-only ergonomics.

## Compatibility and migration

This pass is additive except for compatible strengthening of TypeScript result
types. Canonical JSON, schemas, runtime operation names, WASM ABI, C ABI, Zig
one-exercise results, package name, and documented v0.1 imports remain valid.
Migration consists of binding repeated context in `createProgram`, replacing
literal measurements with helpers, and optionally moving direct calls beneath
`runtime`. A migration guide will show both forms. No v0.1 API is removed.

## Evidence and documentation

Tests will cover measurements and exact decimals, injected clock/IDs, generated
canonical requests, high/low-level differential equivalence, lifecycle and
reload, revision conflicts, type narrowing, presets, discovery, old aliases,
package exports, Node/browser packed consumers, multi-exercise Zig, and existing
C conformance. Examples will cover recommendation, full lifecycle, persistence,
deterministic providers, and direct canonical use. Documentation will add the
v0.2 quickstart, lifecycle, runtime/canonical, determinism, methodology,
migration, Zig, and C guidance.

After implementation, the API will be reviewed from TypeScript, Zig, and C
consumer perspectives. Validation will use focused tests during development,
then formatting, package build/declaration inspection, clean consumers,
`zig build check`, and `zig build check-release` as required by repository
policy. Failures and intentionally deferred friction will be recorded in the
final report.
